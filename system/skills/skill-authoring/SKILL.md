# 스킬 작성 매뉴얼

스킬 = **케이스별 사용 매뉴얼**. 도구·템플릿 위에 얹혀 "이 상황에선 이렇게" 를 담는다.
색인(name·description)은 매 턴 주입되고 본문은 `get_skill` 로 그때만 로드된다 — 즉
**description 은 상시 비용, 본문은 호출 비용**이다. 이 비대칭이 아래 규칙 전부의 근거다.

## 1. 컨텍스트는 공공재

본문은 시스템 프롬프트·대화 history·다른 스킬 색인·실제 요청과 **같은 창을 나눠 쓴다.**

- 기본 가정: **모델은 이미 똑똑하다.** 모델이 이미 아는 것은 넣지 마라.
- 매 문단에 물어라 — *"이 문단이 토큰값을 하는가?"* 못 하면 지운다.
- 장황한 설명보다 **짧은 예시** 하나가 낫다.
- 넣을 가치가 있는 것: 모델이 알 수 없는 것(우리 규약·이 API 의 함정·실측으로 확인된 계약).

## 2. 자유도를 과제에 맞춰라

절차가 깨지기 쉬울수록 좁게, 여러 길이 다 맞으면 넓게. 절벽 옆 좁은 다리엔 난간을 달고
열린 들판엔 길을 여러 개 둔다.

| 자유도 | 형태 | 언제 |
|---|---|---|
| **높음** | 원칙·판단 기준을 글로 | 여러 접근이 다 유효, 맥락이 결정을 좌우 |
| **중간** | 정해진 패턴 + 파라미터 | 선호하는 방식이 있고 변형은 허용 |
| **낮음** | 고정 절차·정확한 호출 순서 | 깨지기 쉽고 순서가 중요, 일관성이 정확성보다 우선 |

판단(무엇을)은 모델에게 남기고 절차(어떻게)만 좁혀라 — 반대로 하면 스킬이 모델을 바보로 만든다.

## 3. description = 트리거 (상시 주입, 가장 비싼 줄)

이 한 줄로 모델이 "지금 이 스킬인가" 를 판단한다. 세 조각을 다 넣는다:

1. **무엇을 하는 스킬인가** (한 문장)
2. **태그** — 사용자가 실제로 칠 법한 한국어·영어 표현 (검색 매칭용)
3. **쓰지 말 것** — 인접하지만 아닌 경우

3번을 빼면 **오발동한다.** 긍정 트리거만 있는 설명은 비슷한 요청 전부를 끌어당긴다.
실측된 실패 형태다 — 차트·스케줄 요청에 빌드 절차가 튀어나오는 식.

```
description: 라이브러리 시험지 PDF → 퀴즈 렌더. 태그 - 시험지, 기출, 퀴즈로, exam, quiz.
  … 쓰지 말 것 — 라이브러리 밖 파일(upstage-ie), 새 문제 창작(그냥 생성).
```

## 4. 본문 구조

정해진 틀은 없지만 잘 되는 순서가 있다:

1. **언제 쓰나 / 언제 안 쓰나** — description 의 확장. 경계 사례를 여기서 못 박는다.
2. **결정 트리** — 축이 둘 이상이면 먼저 분리한다(예: *의도*=신규냐 수정이냐 / *실행*=한 건이냐 여러 건이냐). 섞어두면 모델이 한 축을 다른 축으로 오독한다.
3. **절차** — 번호 매긴 단계. 각 단계는 검증 가능한 행동 하나.
4. **주의·한계** — 정직하게. 엔진 한계는 감추지 말고 적는다.

## 5. 정직 규칙 (반드시 넣을 것)

- **조용한 대체 금지** — 원래 경로가 막혀 다른 수단으로 내려갈 때는 *다운그레이드로 취급하고 사용자에게 먼저 알린다.* 소리 없이 바꾸면 사용자는 원본이 나온 줄 안다.
- **채우려고 발명 금지** — 결과가 없으면 "없음" 이라고 말한다. 빈손이 부끄러워 지어낸 항목이 최악이다.
- **실행하지 않은 것을 했다고 하지 마라** — 도구가 실패했으면 실패로 보고한다. "로그 성공 ≠ 임무 성공."
- **자산 보호** — 스킬이 딸린 스크립트·참조를 들고 있으면, 부족해 보여도 임의로 고치지 말고 물어라.

## 6. 큰 스킬 = 디렉토리 + 참조 문서

본문이 길어지면(거대 API 치트시트 등) 단일 파일은 매번 통째로 로드돼 그 자체가 bloat 다.
쪼갠다:

```
system/skills/<slug>/
  SKILL.md              ← 색인 + 판단 규칙만 (짧게)
  references/<name>.md  ← 상세. 필요할 때만 로드
```

- 본문은 **"어떤 판단을 하고 어느 참조를 읽을지"** 까지만.
- 상세는 `get_skill(slug, reference: "<이름>")` 로 한 편씩.
- 참조 목록은 **자동으로 본문 끝에 붙는다** — 저작자가 목록을 손으로 관리하지 않아도 되고, 잊어서 안 보이는 일도 없다.
- 단일 파일(`<slug>.md`)도 그대로 유효하다. 짧으면 쪼개지 마라.

## 7. 저장

- 사용자 스킬 = `save_skill`(owner 자동). 시스템 스킬은 repo 파일이라 여기서 못 고친다.
- slug = 소문자·하이픈. frontmatter 는 `name` / `kind` / `description` 3개.
- `kind` = design | tool-usage | procedure | persona | policy (색인이 이걸로 묶는다).

## 8. 쓴 뒤 자체 점검

- description 만 읽고 "언제 쓰는지" 가 분명한가? **안 쓸 때**도 적었나?
- 본문에서 모델이 이미 아는 문단을 지웠나?
- 절차의 자유도가 과제의 깨지기 쉬움과 맞나?
- 실패했을 때 뭐라고 말할지 적었나?
